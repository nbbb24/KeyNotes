# 性能分析与常用工具

性能分析的第一步是把“慢”改写成可测量的问题：哪条路径、什么方向、多大数据、多少并发、测量的是提交时间
还是完成时间？

## 核心性能指标

| 指标 | 含义 | 常见单位或场景 |
| --- | --- | --- |
| Bandwidth | 单位时间传输的数据量 | GB/s、GiB/s、Gbps |
| Latency | 完成一次操作的耗时 | μs、ms |
| Throughput | 系统整体有效处理能力 | 请求/s、Token/s、GB/s |
| IOPS | 每秒完成的 I/O 操作数 | 小块读写性能 |
| P50 / P99 | 延迟分位数 | 典型延迟和长尾稳定性 |
| Chunk Size | 单块数据大小 | 传输粒度与分片策略 |
| Batch Size | 每批操作数量 | 聚合提交与固定开销摊薄 |
| Queue Depth | 同时在途的请求数量 | 通信引擎并发度 |
| Overlap | 操作重叠执行 | 计算与通信、复制与复制并行 |
| Full Duplex | 双向同时传输 | 双向带宽和资源争用 |
| PFC | Priority Flow Control | RoCE 网络的优先级流控 |
| NUMA Affinity | CPU、内存和设备亲和关系 | 减少跨 NUMA 访问 |

!!! warning "单位必须明确"

    `Gbps` 是十进制比特每秒，`GB/s` 是十进制字节每秒，`GiB/s` 是二进制字节每秒。端口标称 400 Gbps
    不等于应用一定能得到 50 GB/s 的有效载荷带宽，协议、包头、控制流量和软件开销都会占用能力。

## 常见误区

- 大块带宽高，不代表小消息延迟一定低。
- API 很快返回，可能只表示操作提交完成，而不是数据已经到达。
- 单向带宽正常，不代表双向并发时仍能保持相同带宽。
- 单卡测试正常，不代表多卡共享 PCIe Switch 或出框口时没有争用。
- 平均值正常，不代表 P99 长尾和抖动可接受。

## 分层测量方法

| 层次 | 目标 | 建议记录 |
| --- | --- | --- |
| 内存 | Host DRAM、HBM、片内搬运能力 | 读写方向、块大小、NUMA、并发 |
| 总线 | H2D/D2H/P2P | PCIe 速率与宽度、拓扑、共享关系 |
| 网络 | 节点间单流和多流 | NIC、端口、队列、丢包、重传、PFC |
| 通信库 | Send/Read/Write/Collective | 算法、协议、Rank 数、消息大小 |
| 业务 | KV Cache、模型加载、推理 | 端到端耗时、吞吐、P50/P99 |

先证明底层链路正常，再逐层向上比较额外开销。反过来只看业务总耗时，很难区分计算、复制、网络和同步等待。

## 常用系统命令

| 目的 | 命令 |
| --- | --- |
| 查看 NPU 状态 | `npu-smi info` |
| 查看 PCIe 设备详细信息 | `lspci -vv` |
| 查看 PCIe 树形拓扑 | `lspci -tv` |
| 查看 NUMA 拓扑 | `numactl -H` |
| 查看 CPU 与 NUMA 信息 | `lscpu` |
| 查看网卡接口 | `ip -br link` |
| 查看 RDMA 设备 | `rdma link show` |
| 查看网卡能力和统计 | `ethtool <网卡名>`、`ethtool -S <网卡名>` |

昇腾环境还可以使用对应版本的 `ascend-dmi` 等工具测试 H2D、D2H、D2D、P2P 带宽，或检查 PCIe、HCCS、
RoCE 等链路。命令参数和支持范围随硬件与工具版本变化，应以当前环境的 `--help` 和产品文档为准。


## 自测问题

1. H2D 描述的是方向、API、协议还是硬件引擎？
2. 控制面和参数面为什么不是同一种分类？
3. 跨 Die 是否一定等于跨板卡或跨服务器？
4. 出框口的物理边界应如何确认？
5. RDMA、RoCE 和 Ethernet 分别处于哪个层次？
6. 为什么 NUMA 会影响 H2D 和 Host Memory Offload？
7. API 提交耗时与端到端完成耗时有什么区别？

如果能结合一条真实数据路径回答这些问题，就已经具备继续阅读驱动、通信库和性能日志的基础。
