# 📊 传输性能：先把单位和计时边界说清楚

一个有用的基准测试，要回答明确的问题：在规定的载荷、路径、并发和完成保证下，有效工作需要多久？缺少这些条件的单个“带宽”数字，无法解释真实流水线。

## 🧮 单位与工作负载形态

| 指标 | 含义 | 常见陷阱 |
| --- | --- | --- |
| 带宽 | 每秒完成传输的载荷字节数 | 混淆 bit/byte、十进制/二进制前缀 |
| 延迟 | 每次操作耗时 | 只计提交时间，不等完成 |
| 吞吐量 | 单位时间完成的有效工作 | 统计入队而非完成的任务 |
| IOPS | 每秒完成的操作数 | 比较不同大小的操作 |
| P50 / P99 | 中位数 / 第 99 百分位延迟 | 用平均值掩盖长尾 |
| Chunk / Batch / Queue Depth | 每块字节数 / 一批操作数 / 在途操作数 | 同时改变三个变量 |

1 GiB 等于 $2^{30}$ 字节，1 GB 等于 $10^9$ 字节。20 ms 传输 1 GiB，相当于 50 GiB/s，约 53.69 GB/s。标称 400 Gbit/s 对应扣除协议和系统开销之前的 50 GB/s。全双工测试中将两个方向相加，不能得到单向带宽。

```python
# runnable-example
size_bytes = 2**30
elapsed_s = 0.020
print(size_bytes / elapsed_s / 1e9)  # 53.6870912 GB/s
assert size_bytes / elapsed_s / 2**30 == 50
```

## 🧩 分开测固定开销与持续带宽

使用多个传输大小，拟合粗略模型 $T(S)=L+S/B$。小传输更容易暴露提交与同步开销，大传输更容易暴露带宽。提高 Queue Depth 可以隐藏延迟，直到某个共享资源饱和；之后继续增加并发，可能恶化长尾。在稳定系统中，Little 定律将平均在途任务数与吞吐量、平均延迟联系起来。

冷启动初始化和稳态性能应分开测。明确预热，计时直到完成，验证目标内容，报告重复次数与延迟分布。检查重叠执行时，要看端到端耗时和时间线；异步提交复制与计算，并不能证明硬件同时执行了它们。

## 🔍 Linux 观察工具

以下是适合对应 Linux 环境的只读观察示例，不是要求在所有开发机器上执行的命令。

| 目的 | 命令 | 如何解读 |
| --- | --- | --- |
| NPU 健康状态与身份 | `npu-smi info` | 将可见设备与目标作业对应 |
| PCIe 树与链路细节 | `lspci -tv`、`lspci -vv` | 检查共享交换器件与协商能力 |
| NUMA 与 CPU 拓扑 | `numactl -H`、`lscpu` | 比较设备位置、线程与内存放置 |
| 网络接口 | `ip -br link` | 确认预期接口及状态 |
| RDMA 设备 | `rdma link show` | 识别可用 RDMA 资源 |
| 网卡能力与计数器 | `ethtool <interface>`、`ethtool -S <interface>` | 查看链路及设备特定的错误、拥塞指标 |

受支持的昇腾产品可以使用 `ascend-dmi` 进行带宽与链路诊断。H2D、D2H、D2D、P2P 模式应以安装版本的帮助和[对应昇腾工具文档](https://www.hiascend.com/document)为准，不要假设不同代际支持完全相同的参数。

## 📊 设计可复现的实验

固定硬件、软件、后端、方向、缓冲区类型、NUMA 放置和完成规则。先扫描传输大小，再扫描并发。除了载荷吞吐，还记录 CPU 利用率、可获取的内存带宽、端口计数器和 P99。Host 中转可能先耗尽 DRAM 带宽，共享上行链路也可能限制原本独立的设备。

最后将微基准与应用行为联系起来。如果应用主要发送细小片段，或者在等待 Barrier，提高大块传输带宽未必改善词元延迟。用[端到端模型](end-to-end-transfer.md)决定下一步应该测什么。
